Chapter 6

The save

Everything the game knows about your relationship fits in 256 KB of battery-backed memory on the cartridge. The save format is careful: every block is stored twice, checksummed and compressed, so a save interrupted halfway never loses the one before it.

Six kinds of block

The save is made of blocks, each tagged with four letters:

blocktagholdssize in memory
ALDSDsettings: music, sound and voice volume, text speed504 B
BLDGDthe game itself: names, the calendar, every flag, the three heroines' records15,448 B
CLDODa small header block244 B
DLDPDevent state, written from the save menu4,098 B
ELDFD100 small records written only by the wireless screens196 B each
FLDTGone large record per heroine, most likely the trips5,320 B each

Block B is the one that matters. The game keeps it in memory as one structure, the GameState, and saves it whole.

Two copies, always

Every block has two places on the cartridge, used in turn. Each copy starts with a 32-byte header: a magic number, the stored size, a generation counter, a version, and a SHA-1 hash of the data. When the game saves, it writes to the copy it didn't load from, with the generation one higher. When it loads, it takes the newer copy whose magic, size and hash all check out. If the power fails mid-write, the half-written copy fails its hash and the game falls back to the other one. Save_WriteBlock does the writing (it was labelled as a sprite function until we proved what it does).

Packed, then compressed

Before a block is written, overlay 0 packs it (Ov00Init_PackSaveB and its siblings). Packing splits the structure into sections and rearranges its fields down to the bit: narrowing numbers, folding flags together, splitting records. Block B goes into 73 sections. Then the packed block is compressed with Nintendo's LZ compression (MI_CompressLZImpl), or stored as it is when compression wouldn't make it smaller.

About 200 small routines do the packing. Rather than read them all, we let the game describe itself: the game's own packer and unpacker were run on test patterns, where pattern k sets every input bit whose number has bit k set, each paired with its opposite. Every output bit then gives away which input bit it came from. The result: each kind of block is a pure rearrangement of bits, with one exception, a run of 167 bytes that are saved as true or false.

What it remembers

A few things in the GameState:

  • Your names. Two name fields, filled from the profile you write by hand.
  • Where the story stands. A field records whether you're in the main story or have become her boyfriend.
  • When you last saved. Year, month, day, weekday and time, which the game compares with the clock (chapter 4).
  • A block per heroine. Each of the three gets 1,672 bytes of her own: thousands of flags (bits), counters (bytes), larger values (words), and her record.

Flags work in a slightly surprising way. A flag that belongs to no one in particular is written into all three heroines' blocks, and read back from Manaka's (GameFlags_SetScopedBit). There's no separate global block; there are three copies.

Her record

Each heroine's record (GameState_GetSlotPtr) is where the relationship lives:

fieldwhat it is
flagswhether you're together; whether it ended
phasethe relationship stage, 0 to 2: the column every scene table in chapter 3 is indexed by
affectiona value from 0 to 255, shown as hearts. SaveSlot_GetLevelFromPoints turns it into 0 to 16 hearts, with a threshold table per heroine
love pointsonce you're together, a second, larger counter (SaveSlot_AddPointsClamped) with 20 levels, from 100 points up to 35,500
morea mood byte, counters, timers and small tables still being read

In lp-engine

The save is a plain 256 KB file, saves/loveplus.sav, byte for byte what a cartridge would hold. That makes saves portable: Game > Import Save takes one dumped from a real cartridge or from DeSmuME, and Export Save gives it back. The game writes the save itself, exactly as on the DS; the engine stores the result. lp-engine also has its own reader and writer for the format, used by its tools and tests.

How we know

  • Our compressor produces the game's exact bytes on every recorded block. Matching it took the game's own search order: farthest match first, never closer than two bytes, at most 18 bytes long.
  • For every kind of block, across several slots and every copy and generation state, our card writer and the game's Save_WriteBlock produced identical bytes: 30 writes out of 30.
  • Saves edited by our writer boot in the game, which then holds exactly the GameState we wrote: 15,448 bytes out of 15,448.

Still open. Blocks D and F are proven against the game's code, but no real save we have contains them yet. They belong to the later part of the game, after you start going out. Block E is written only by the wireless features. Many single bytes in the heroine record are typed but not yet named. The details are in docs/SAVE_FORMAT.md and docs/SAVE_RECORD.md.

Where everything sits

Block kind k has some number of slots, and every slot has two copies. The addresses are offsets into the 256 KB backup memory:

The copy header

offsetfield
+0x00magic 0x10190573
+0x04stored size
+0x08generation, 16 bits
+0x0aversion: 3
+0x0cSHA-1 of the stored bytes (20 bytes)

A block that was never loaded counts as copy 0, generation 0, so its first write goes to copy 1 with generation 1. Every recorded cartridge shows exactly this.

Compression, to the byte

To produce the game's exact bytes, an LZ compressor has to make the same choices as SearchLZ. It searches the 4 KB window farthest first, never matches at a distance under 2, replaces its best match only with a strictly longer one, and stops at 18 bytes. The game pads its buffer to 4 bytes but stores the unpadded length.

Packing

A packed block is a series of sections. The first entry of each section is its size. Section 0 also carries the tag, version and structure size, which the unpacker checks before it trusts anything else. Every packed bit is a direct copy of one bit of the structure, with a single exception: 167 bytes of block B are stored as true-or-false (unpacked as "not zero", packed as "equals one"). Two fields the game keeps at −1 in memory are never saved and load as 0.

The GameState

offsetholds
+0x0008a 16-byte name (text variable 0x1b)
+0x0018the player's name, {v0} in the scripts
+0x0078the relationship and calendar mode: main story or going out
+0x0180the tick count when the game was loaded
+0x1224three heroine blocks of 0x688 bytes, Manaka, Rinko, Nene

Inside each heroine's block, flag n is bit n from the start, counter n is the byte at 800 + n, word n is at 0x360 + 4n, and her record starts at 0x3a0. A global flag is written to all three blocks and read from Manaka's. A global counter lives only in Manaka's block.

The record's numbers

Affection (0 to 255) becomes hearts through a 17-step threshold table for each heroine (SaveSlot_GetLevelFromPoints). Love points, used once you're together, climb from level 1 to level 20, crossing thresholds at 100, 250, 750, 1,200, 2,500, 3,500, 5,000, 7,500, 9,999, 13,000, 14,500, 16,250, 18,250, 20,500, 23,000, 25,750, 28,750, 32,000 and 35,500 points. Her state byte becomes one of five steps through tables indexed by her relationship phase. Most of the other 70 or so named fields are counters, timers and small tables that the event stages read.
