Chapter 13

What we don't know yet

The game runs from start to finish in lp-engine, but running it and understanding it aren't the same thing. Large parts still run as the game's own code, correct because they're the original, but not yet explained. This is the list.

Two kinds of gap are worth keeping apart. Some are gaps in understanding: the engine runs the game's code faithfully, and we just can't yet say what that code does. Others are gaps in evidence: we've read the code and believe we know, but no recording of the real game has shown it happening. Each item below says which kind it is.

Whole systems

These are the biggest gaps. All of them work in lp-engine, because they run as game code, but none has a chapter in this guide yet, because we can't explain them to the standard the other chapters hold to.

Inside systems we do explain

Choosing scenes

  • The event definitions. mail/condition.bin's 1,028 records: the context mask is read, the other fields aren't. Nor is the mapping from an event number to the scene id it starts. Understanding.
  • The leaves. The 36 stages and 107 condition operations are exact, but the values they read come from smaller functions (calendar rules, schedule state, ranking) that are documented, not ported and re-checked. Understanding.
  • 69 script commands (4% of uses) have a known chain of effects but haven't been watched working. Most argument units, such as how many frames a blend takes, are inferred. Only the wait was measured. Evidence.
  • The task kinds. The script machine queues 195 kinds of task (chapter 3). What each kind does every frame is mostly unread. Understanding.

The game's shape

  • The room's own machine (overlay 35): every action, its result, and what it reads. Only the tap path is fully known. Understanding.
  • Several overlays are known by their files but not their screens: 20 and 42 (both clock setting), 22, 37, 38, 41, 43. Understanding.
  • Scene exit code 6 has only ever been forced, never seen in natural play. Code 7 seems unreachable. Evidence.

Time

  • The calendar's moving codes. All 175 codes are mapped to their days, but some year-dependent ones, covering 8 to 23 days a year, haven't been named. Understanding.

The save

  • Blocks D and F are proven against the game's code, but no real save we have contains them. Both belong to the later part of the game. Evidence.
  • The heroine record's long tail: about 110 single bytes near its end are typed (we know their sizes and which functions use them) but not named. Understanding.

The heroines

  • The eye track. Motions carry a visibility track that looks like eye requests. The game's idle eye timer is decoded, but whether the track feeds it isn't confirmed. Evidence.
  • Camera presets. The light angles are decoded. Some of the position fields, and how transitions between presets move, are only partly read. Understanding. lp-engine runs the game's own camera code, so the picture is right regardless.
  • Costume corners. Some shading-table variants and colour palettes. Understanding.

Sound

  • Sound driver features the game hasn't been seen to use: capturing output, pulse and noise channels set up by the game, surround. The hardware's sample-and-hold sound isn't imitated: the engine interpolates instead. Evidence.

Text

  • Some minigame graphics (name tags, stage names, the pause menu) and a few rarely seen images still show Japanese. Translation work, not research.

What still runs as the game's code

This isn't really a gap in understanding, since game code is correct by definition, but it is the measure of how far the port has come. In the measured runs (chapter 12), 3,583 distinct functions still ran as interpreted ARM code. The heaviest are the voice decoder (lp-engine already has a native one, not yet wired into the runtime), NitroSystem's 3D drawing, memory copies, the sprite manager and the SDK's thread switching. The registry also lists 143 named functions waiting their turn.

How to help

Most items marked evidence need saves that reach later parts of the game: a lovers-phase save with a trip or a stay, a save made just before a dream, or recordings of the minigames. If you have a save from a real cartridge that gets that far, an issue on GitHub saying so could turn several of these into facts. Most items marked understanding start the same way: pick the function in the function map, follow its callers, and compare against the engine running the scene with game_probe (chapter 12).

The detailed lists live with the work: docs/SCRIPTS_LEDGER.md (scripts and events), docs/GAME_FLOW.md (game flow), docs/SAVE_FORMAT.md (save), docs/NATIVE_COVERAGE.md (port).
