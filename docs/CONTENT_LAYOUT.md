# Content architecture

Goal: the user supplies their own ROM **once**; the engine then runs from the game's own files only. Three layers, with the
boundary between them kept strict (nothing from the ROM is ever committed):

| layer | tool | reads | writes | purpose |
|---|---|---|---|---|
| 0 extraction | `tools/lp_extract.py ROM.nds content/` | the ROM | `content/` | the game's own files, undone only where the ROM's container format demands it |
| 1 engine loaders | `engine/` (Rust crate `lp_engine`) | `content/` (+ `patch/` overlay) | - | parse the native formats directly; each loader is diffed against its Python parser/oracle |
| 2 tools | `tools/lp_export.py content/ export/` | `content/` | `export/` | conversions to common formats and translation interfaces; separate from the engine, regenerable |

## Layer 0: `content/`
Does only what the ROM's containers require, and never interprets content:
- NitroFS files are written at their ROM paths under `assets/`; archives (header `18 56 01 00`) are unpacked one level into directories (LZ decompressed). Raw files (NCGR/NSBMD/SDAT/SSEQ/GTD/voice banks ...) stay as the game has them.
- Reversible obfuscation is removed: the SBIN/TXRC stream cipher (`assets/arc/tmx_event.arc/*.sbin`, `assets/text/*.txrc` are plain), BLZ compression of the ARM9 and the overlays.
- Data that lives inside the game's code (no file exists for it) goes to `engine/`: the code images, `memory_map.json`, the table catalog `tables.json`, `strings.json` (embedded Japanese strings), `face_tables.json`, `text_rules.json`, `motion_table.json`, `script_resource_map.json` (script id -> arc entry pools), `g7221.pack` (voice decoder tables).
- `manifest.json` records ROM identity and per-stage counts. Local analysis products generated by tools (`engine/event_selection.json`, `stage_tables.json`) also live in `engine/`.
- `tools/lp_paths.py` is the Python helper for locating things (script directory built straight from script 899).

## Layer 1: engine loaders
Loaders so far (each verified against its Python counterpart):
- `script.rs`: SBIN VM; trace-identical to `tools/lpvm.py` on all 16,332 entries (`tools/script_trace_py.py` vs `script_trace`).
- `text.rs`: TXRC; all 8 system text resources, 22,413 lines, identical to `tools/txrc.py`.
- `nns2d.rs`: NCLR/NCGR/NSCR/NCER/NANR; the `nns2d_dump` bin reproduces all 2,665 resource sets (13,959 PNG/JSON files) pixel- and value-identical to `tools/nns2d_export.py` in 3 s (Python: minutes). `tools/loader_check.sh` re-runs every diff (and the Rust tests); `cargo test` covers the formats with synthetic data (no ROM bytes needed).
- `nns3d.rs` (+ `bytes.rs`): NSBMD models (nodes, materials, shapes, display lists, structure byte code, envelopes), NSBTX texture decoding (all DS formats), NSBCA joint animations, NSBVA visibility. `nns3d_dump` vs `tools/nns3d_dump.py`: 4,503 files, 1,780 meshes (skinned, bind pose), 4,823 textures, 7,454 joint animations, 2,553 visibility animations identical.
- `heroine.rs`: costume parts, motions by name-matched joints, expressions (texture swaps), colour variants, toon/edge tables. `heroine_dump` vs `tools/heroine_dump.py` identical for 3 heroines x 7 configurations (outfit/hair/motion/frame/mood/variant/time of day).
- `camera.rs`: the 150 camera presets (`camera_data_N.bin`, light angles).
- `render.rs` + `viewer` bin: wgpu toon renderer (per-vertex light index into the toon table, texture modulation, alpha test, polygon-id edge pass, supersampled blit). `tools/viewer_parity.py` compares it with the reference numpy rasteriser: mean difference 0.13-0.23 / 255 on all three heroines, including an animated pose. `viewer CONTENT --png out.png` renders headlessly; without `--png` a window opens (orbit, zoom, motion/outfit/hair/mood/time-of-day keys). `tools/viewer_sample.py` builds the sample sheet.
- **Enhanced rendering (alternate mode, authentic stays the default and the verified one):** `RenderOpts` in `render.rs` + `upscale.rs` + `tessellate.rs`. Switches: per-pixel toon (stepped or smooth over the game's own ramp), Lanczos-3 texture upscaling with mips and 16x anisotropy, outline radius in pixels, rim light, perspective camera, curved-PN-triangle tessellation with crease-aware shading normals, any output size (`--width/--height/--ss`). `viewer --look authentic|filtered|clean|clean-s|soft|soft-s|wide|cel` or the individual flags; `tools/viewer_hd.sh` renders the comparison set. Findings: texture filtering and per-pixel smooth toon give the biggest gains; PN smoothing rounds jaw/hair silhouettes; hard cel banding looks bad because the models' normals are not authored for it.
- **Performance** (`viewer --bench N`, one animated heroine, M-series MacBook Pro via Metal, all frame work in the loop): authentic 4K ~5.8 ms/frame serial (174 fps); enhanced `clean-s`/`soft-s` at 4K with 2x supersampling (82k triangles, 7680x4320 scene) ~13-14 ms serial (~75 fps), ~8.2 ms pipelined (~122 fps). CPU-bound: pose 0.9, PN tessellation 3.7, buffer build 2.1, encode 1.5, GPU 5-6 ms. A bench-found bug (variant textures re-decoded and re-uploaded every frame, 148 ms) is fixed by caching them per wardrobe.
- `loader_sample CONTENT OUT` renders a screen composite and an animated cell strip and prints system text, straight from `content/`.
 Every further loader follows the same pattern: native format in, structured data out, diffed against its Python counterpart (`nns2d.py`, `nns3d.py`, `sdat.py`, `sseq.py`, `nftr.py`, `gtd2png.py`, `txrc.py`, `term.py`). The engine reads `patch/<same relative path>` before `content/`, so translations and fixes are plain file replacements.

## Layer 2: `export/` (not read by the engine)
`lp_export.py` stages: `scripts` (event directory JSON), `strings` (per-script dialogue string tables, the translation interface), `text` (system/UI/mail text JSON), `graphics` (GTD -> PNG), `nns2d` (screens/tile sheets/cells as PNG + JSON), `nns3d` (models/motions/expressions/shading as glTF + JSON, camera presets), `sound` (WAV, banks JSON, MIDI, SoundFonts), `fonts` (NFTR -> PNG + JSON). Dialogue patchers, model/texture swappers and script editors belong here (importers must round-trip to the native bytes).

## Output layout
```
content/   manifest.json  assets/<ROM paths, archives unpacked, cipher removed>  engine/<images + code-embedded tables>
export/    scripts/ strings/ text/ graphics/ models/ camera/ sound/ fonts/ export_manifest.json
```
`tools/validate_content.py content/ export/` checks both trees.

## Engine data
Nothing embedded in the game's code/data is lost: the full images are dumped, and tables are addressed by `(module, RAM address)` through
`tools/lp_engine.py` (`Engine(content).u32('static', 0x21067f0)`, `.table('event_id_table_kind3')`, `.cstr(...)`). Overlays that share a base
address are separate modules (`ov05`, `ov41`, ...). The catalog `data/engine_tables.json` is metadata only (addresses, size estimates, kind,
referencing functions) and is committed; it is generated by `tools/build_engine_catalog.py` from the analysis outputs. Names are added as tables are
identified. Hard-coded text is rare: UI/dialogue text lives in `text/` and `strings/`; the binary only embeds names, kana tables and the speech/keyword vocabulary
(overlays 5, 37, 38, 41), listed in `engine/strings.json` for translators. `tools/validate_content.py content/` checks the tree (images vs sha1, catalog bounds,
event-id tables resolve in the script directory, G.722.1 tables, embedded strings).

## Translation / patching design
- Scripts are never edited. The engine reads the native script string table; a text op (`81 buf off32`) is looked up in `patch/strings/<script>.json[off]` first (a small, documented patch format the engine owns; `export/strings/` is both the reference dump of the originals and the starting point for a translator's file). Offsets are stable because the binary is untouched, so longer English text needs no relayout.
- `text/*` resources likewise: native TXRC in `content/assets/text`, overridable per file or per `[group][sub][line]` from `patch/`.
- Strings carry variables (`{vN}` from string vars, `[p-name2]`-style placeholders in TXRC text, `\r\n` line breaks) that a translator must keep.
- Needs engine-side work for English: a Latin font (the game uses bitmap dot fonts), proportional layout / word wrap instead of fixed 2-byte cells, and text box sizing. Voice stays Japanese.

## Rules
- The extractor reads only the user's ROM; outputs live under `content/` and `export/` (gitignored). No ROM-derived data is committed to the repo.
- Every stage records counts in `manifest.json`; the engine refuses to start if the manifest version is older than it expects.

## Heroine rendering rules (verified)
- A heroine = body + larm + rarm + waist + leg (`X_01_NNN_*`), hair (`X_00_NNN_hair`), face (`X_base_face_m/l`), hands (`X_base_lhand/rhand_*`), optional item.
- Each part has its own skeleton chain with a different joint order; a motion's tracks must be applied **by joint name**. Track -> parts: `body`: body+face, `larm`: larm+lhand, `rarm`: rarm+rhand, `leg`: leg+waist, `hair0/1/2`: hair (19/20 joints), `item`: item.
- Visibility tracks (`bits[frame*nodes+node]`) hide/show shapes per NODE; eye00/lhand/rhand tracks switch eye and hand meshes. A NODE's default visibility comes from the structure byte code.
- Joint animation: keys every 1/2/4 frames then per-frame tail, linear interpolation; assumed 30 fps.

## Expressions and per-model companion files (verified)
- Game bundle container (used by `async3d.arc` motions and the model companion files): `{count u32, entry_size u32 = 0x28}` then entries `{offset u32, size u32, name[32]}`.
- **Expressions are texture swaps**, not texture-pattern animations. The face model has materials named `<p>_eye.0`, `<p>_brow.0`, `<p>_cheek.0`, `<p>_mouth.0` (+ `<p>_face_NN` skin). Selecting an expression rebinds a slot to texture `<p>_<slot>.<n>` and its `<name>_pl` palette. Variants: eye 0-22 (stored in `async3d.arc`), brow 0-5, cheek 0-1, mouth 0-11 and face-skin variants (in `tm_model_block_base.arc`). Mouth variants are the lip-sync visemes (driver not yet decoded).
- `.tmbsd` (120 B) = 40 RGB triplets, one 5-bit channel per byte: first 32 = toon table, last 8 (at +0x60) = edge/outline colours; the game ORs them into RGB555 and feeds `G3X_SetToonTable`/`G3X_SetEdgeColorTable`. The `_0/_1/_2` suffix and the `plt_NN` variants select different tables (meaning of the three states not yet decoded).
- `.tmbpl` (32 B) = 16-colour RGB555 palette (hair colour variants `ha1_NN`).
- Motion counts are real: async3d holds 437 distinct motion ids for Manaka, 49 for Rinko and 63 for Nene (each stored twice: once as nsbca and once as nsbva bundles); Rinko/Nene ids are almost all a subset of Manaka's.

## Rendering rules (decoded from the game code, verified by renders; reference implementation: tools/toonrender.py + tools/heroine.py)
- **Time of day** (0 day, 1 evening, 2 night; the game remaps its background time phase 1,2,0 -> 0,1,2) selects `<model>_<S>.tmbsd` / `plt_NN_<S>` tables. `tm_model_block_base` `<p>_base_<S>`: toon[32] is a tint ramp (warm / pink / blue-violet shadow colour rising to white), edge[0] = skin outline.
- **Toon shading**: polygon attr bits 4-5 == 2. Per-vertex R-channel light intensity (diffuse * light colour * max(0,-N.L), lights enabled by attr bits 0-3, 5-bit) indexes the toon table; the table colour modulates the texture. Light colours 0x7fff/0x4210/0x2108; light directions = 3 yaw/pitch pairs from the camera preset (`camera/presets.json`), start vector (0,0,-1), rotate Y then X.
- **Outline**: DS edge marking, colour = edge[polygon_id >> 3] (face/skin id 1-2 -> 0, clothes 8.. -> 1-5, hair 48 -> 6, ribbon 56 -> 7). Ownership of the 8 edge entries: base bundle 0, hair bundle 6-7, outfit bundle 1-5 (`plt_NN` bundle replaces it for colour variant NN).
- **Colour variants**: hair colour NN>=1 replaces the hair palette with `<tex>_NN.tmbpl` (18 colours); ribbon = sub-texture `<hairtex2>_0<n>` (7); outfit texture variants `<tex>_<group><variant>` (see `models/variants`), fallbacks `_10`, `_1<variant%10>`.
- **Hands**: `<p>_base_lhand_NN` / `rhand_NN` (17 poses, in async3d); a motion's `lhand`/`rhand` visibility track keeps nodes 0-2 on and one node >= 3 visible: pose = node - 3. The `eye00` track (22 nodes): nodes 0-4 form a constant group ({0,2,3,4} or {0,1,2,3,4}) and at most one node >= 5 is active at a time, changing over the motion (13 = default, e.g. 13->20->5->19->21->13). It is therefore a per-motion timeline of eye *request codes* feeding the game's eye state machine (struct at model+0x488, request at +0x2c, column = request). The exact node -> eye-table column mapping is NOT verified (candidates: column = node-5; node 13 = default); the renderer does not use it and drives the eyes from mood + blink instead.
- **Face**: mood id (0..44, `engine/face_tables.json`) -> brow, cheek, mouth row; eye variant = eye_table[mood][column] (column 0 default, 2 = blink-closed); mouth = row[col[next_mode[viseme]]]. Lip sync: `lipsync/lipsync.dat` bytes (0 a,1 i,2 u,3 e,4 o,5 rest) mapped linearly over the clip, forced to rest while the voice stream peak is < 1000. Script motion command 0x5d(a0): a0 = motion index (0-738 Manaka, 739-840 Rinko, 841-973 Nene) -> `models/motion_table.json` gives the exact motion stem and the default mood; script command 0x34(a0) sets the mood id directly (all 45 values occur in scripts). Blink interval/hold tick tables are in face_tables.json (tick rate assumed 30/s).
- No texture-pattern/material animations exist (no BTA/BTP/BMA); expressions are texture swaps only.
- `tm_model_label.arc` (430 files) = per-part resource descriptors (first u16 = first file index of the part's file set in the heroine's block3d arc); not needed when names are used.
- **Hair animation track** is chosen by the hair model's joint layout: `ribon` joints (20) -> `hair1`; `lpig`/`rpig` (19) -> `hair0`; `hairT_*` joints (19) -> `hair2`; verified by joint-by-joint animation-frequency alignment (hair2 nodes 10-18 equal hair0 nodes 6,9-16) and by renders.
- **Update rate**: the main loop waits `divider` vblanks per frame (`VramBank_Process`: 2 when the 3D capture phase count is 2, else 1). Event/dialogue scenes use the two-phase capture, so they run at 30 updates/s; animations advance 1.0 frame per update (speed 0x1000), which makes the 30 fps assumption for motions, blink ticks and lip hold (20 updates) consistent. The date scene uses three-phase capture (divider 1, 60/s).
- **Script commands**: 0x34(a0) = set face mood (a0 in 0..44, 31k uses); 0x5d(a0) = play motion index a0 (0-973, resolves through `models/motion_table.json`).
- Lip sync progress = decoded codec frames / total frames of the clip (linear over the clip), as implemented in `face_tables.lip_viseme`.
- Open / unverified: the eye00 node -> column mapping; the toon ramp has not been compared against a hardware capture; the 30 updates/s figure is inferred from the frame-divider code (the divider depends on the 3D capture phase counter, so it was not measured at runtime).
- **Idle eye requests (code-driven, decoded)**: the idle loop (`MapCtl_UpdateAnimLoop`) runs a small timer machine (state at 0x21544d8, init `Timer_InitRandomDelayState(flag)`): delay 90-209 ticks (flag 0) or 30-89 (flag 1) in the default state (request code 9); then a short request of 10-19 ticks (code 1 with 20 % probability else 0 when flag 0; 1 or 0 by flag when flag 1), then back to 9. The request code is passed to `Model_RequestMotionState` (codes 12-14 are mapped to 2) and stored as the eye mode (`+0x28`); in the open state the eye texture is `eye_table[mood][mode]` (so default code 9 -> column 9, glance codes 0/1 -> columns 0/1), the blink uses column 2 as described above. Requests also come from script task code (e.g. command 0x4e sets request 9). The `eye00` BVA track is not read by this machine; whether it also feeds requests remains unconfirmed.

## Music player (tools/sseq.py)
- Interpreter for NITRO-Composer sequences (all 152 sequences run with no unknown opcode): 48 ticks per quarter note; note/wait/prg/tempo/volume/volume2/main volume/pan/bend/bend range/transpose/priority/note-wait/tie/mute/portamento/sweep/modulation/envelope; opentrack/jump/call/ret/loop_start/loop_end/alloctrack/fin; random (0xA0), variable (0xA1), conditional (0xA2) prefixes; 16 local + 16 global variables; tracks run in ascending number each tick (a higher-numbered track opened by a lower one runs in the same tick). The tempo is player-wide, the last tempo command at a tick wins.
- Binary encoding: 0x00-0x7F note (key, velocity, varlen length); 0x80 wait, 0x81 prg (varlen); 0x93 opentrack (u8 track, u24 offset), 0x94 jump, 0x95 call (u24); 0xB0-0xB6 setvar/addvar/subvar/mulvar/divvar/shiftvar/randvar (u8 var, s16 value), 0xB8-0xBD cmp_eq/ge/gt/le/lt/ne; 0xC0 pan, C1 volume, C2 main volume, C3 transpose (s8), C4 bend (s8), C5 bend range, C6 prio, C7 note-wait, C8 tie, C9 porta key, CA-CD mod depth/speed/type/range, CE porta on/off, CF porta time, D0-D3 attack/decay/sustain/release, D4 loop_start, D5 volume2, D6 printvar, D7 mute; 0xE0 mod delay (u16), E1 tempo (u16), E3 sweep (s16); 0xFC loop_end, FD ret, FE alloctrack (u16), FF fin. Sequence offsets are relative to the data start (file offset in the DATA block).
- `export_all` (extractor stage) writes `sound/midi/<name>.mid` + `index.json` (tempo map, tracks, loop points, seconds): intro plus one pass of the loop, loopStart/loopEnd markers. MIDI: track n -> channel n (channel 9 skipped, drum-set instruments on 9), CC7 volume, CC11 volume2, CC10 pan, pitch bend + RPN range, CC1 mod depth, program = bank program number & 127 (the bank's programs are not General MIDI instruments).
- Synthesizer (`render`): bank/wave lookup (PCM, key-split, drum-set, PSG pulse, noise), pitch from original key (checked against the measured fundamentals of the wave data: errors <= 0.1 semitone), squared volume law for velocity/volume/expression/main volume, ADSR with decay/release speeds in dB/ms fitted to the manual's table and exponential-in-dB attack, pan, pitch bend, loops. Not rendered: vibrato/tremolo modulation, portamento/sweep glides, SND voice stealing. Verified: structure (87.5 % of 106k notes start on a 32nd-note grid, loop ends align across tracks, MIDI note on/off balanced); by-ear verified by the user (2026-10-12, "sounds better than any DS DAC could hope to achieve").
- **Instruments for the MIDI files**: `sound/soundfonts/<BANK>.sf2` (tools/sf2.py, one SoundFont per SBNK bank, built from the game's own samples: loops, original keys, key splits, drum sets, pan and ADSR). Use the sequence's bank (`sound/midi/index.json` -> `bank` id -> `BANK_*`) with its `.mid`; e.g. `fluidsynth -ni -F out.wav -r 44100 BANK_BGM_001.sf2 BGM_001.mid`. The MIDI program number = SBNK program number and drum sets are ordinary presets (tracks never use channel 9). Validated by loading in FluidSynth 2.6.1.

## Fonts and text engine (tools/nftr.py, tools/textlayout.py)
- **Fonts**: two NFTR bitmap fonts live in NitroFS (`test_font/LC10_UTF8_R90.NFTR`, `LC12_UTF8_R90.NFTR`; no other font file exists, the calendar/time numerals are images: DotFont). Both: 3,833 glyphs, 1 bpp, UTF-8 character codes (Unicode code points), glyph bitmaps stored rotated 90 degrees (R90), monospaced (LC12: half 6 / full 12 px; LC10: 5 / 10), cell 11x11 (LC12) / 9x9 (LC10). Coverage: ASCII 0x20-0x7E, hiragana, katakana, full-width forms, Greek, Cyrillic, ~1,800 CJK; every character of the game's 48,695 strings is covered except `\x17` and U+E724 (both appear once, as lone strings, drawn with the fallback glyph). The extractor writes `fonts/<name>.json` (metrics, `cmap_ranges` = [code_start, code_end, first_glyph], per-glyph [left, glyph width, advance]) and `fonts/<name>.png` (atlas, 64 columns, cell (cell_w+1) x (cell_h+1), display orientation) plus `engine/text_rules.json`.
- **Glyph tricks**: in LC12 the Greek letters are special glyphs: alpha = `!?`, beta = `!!`, gamma/delta = opening/closing quotation marks (used in 42k lines of dialogue: e.g. `gamma...delta` quotes, `...alpha` after an exclamation). In LC10 they are real Greek letters.
- **Rendering rules** (text canvas is rotated 90 degrees because the game is played held sideways; rules below are in reading orientation): strings are UTF-8 (1-3 bytes per character), advance = half width for ASCII, full width otherwise; backslash draws nothing and toggles text colour between the box colour and palette entry 3 (red); newline inside one canvas (`Text_DrawString`, used by UI labels) = line pitch 12 px and every following line starts 6 px left of the first line (the message window uses one canvas per line instead: boxes at BG tiles x = 5, 3, 1 / y = 1, canvas 2 x 20 tiles, i.e. a 16 px line pitch and no indent); no wrapping or kerning (authors insert the newlines: 8,255 lines are exactly 13 full-width characters = 156 px). Three font modes: 1 = LC12 UTF-8 (default), 2 = LC10 UTF-8, 0 = LC12 with Shift-JIS strings (ASCII mapped to full-width, advance 12).
- **Message box**: 3 lines visible; messages are split at newline into 64-byte line slots (max 63 UTF-8 bytes per line); longer messages scroll up one line per advance. Typewriter: one character per drawing step (two in fast mode), interval in updates per character by speed setting 0..4 = 10, 8, 4, 2, 1 (speed -1 = instant). Script text is built in three buffers (0 message, 1 sub label, 2 speaker name; see the script VM notes) with `{vN}` string variables substituted (v0 = player name).
- **Reference implementation**: `textlayout.layout / page_states / typewriter_times / render / check_message` (the last one reports lines over 63 bytes or characters outside the 3-byte UTF-8 range). Verified visually: kana/kanji lines, hanging indent, `!?`/`!!`/quote glyphs, highlight colour, ASCII text.
- **English patch notes**: ASCII glyphs exist in both fonts, so English needs no new font, but they are monospaced (6 px per character at LC12: about 26 characters in the usual 156 px line, 3 lines). The 63-byte line slot is a hard limit; 4-byte UTF-8 is unsupported. A port with its own renderer can use the proportional metrics of a replacement font and wider boxes. Translated strings go into `patch/` (same relative paths), no ROM edit needed.
- **Canvases (enforced limits)**: the text system creates fixed 1-line canvases (`TextCanvas_InitForBG`): 3 message lines per screen, each 13 full-width characters = 156 px; a speaker name tag canvas of 4 full-width characters (48 px: every speaker name in the scripts is at most 4 characters, e.g. フロント, 音楽教師); a 6-row panel of 13-character rows (choice/list menus). Text wider than a canvas is broken automatically: `textlayout.wrap()` implements the line builder (characters are added while the width so far is below 156 px, an explicit newline ends a line, a newline right after a full line is swallowed, and kinsoku: if the next character is one of `! ' , . ?` or one of 。、！？「」【 (text resource group 1, entry 7) the last character of the line moves down with it). Check: of the game's 48,695 strings only 36 (long unbroken monologue lines) are changed by wrap(); every other string is already pre-wrapped to the canvas width, which confirms the 156 px width and the break rule. English text is broken by characters, not words, so a patch should insert its own newlines at word boundaries (at most 26 ASCII characters per line).

## Emulator ground truth (tools/emu_driver.py, py-desmume 0.9.12, headless)
Measured by driving the real game (touch coordinates are raw bottom-screen coordinates; the console is held sideways, see `page_to_touch`):
* Text: typewriter = 8 frames/char at 60 updates/s in 2D scenes; tapping the window completes the current text, then advances. LC12 layout matches pixel-exact (advance 12, line pitch 16, no indent, origin x=8).
* Choice menus: choice boxes are drawn across both pages; the number badges lie on the touch screen. First tap on a badge (choice 1 = touch (180,16), choice 2 ≈ (115,16), choice 3 ≈ (51,16)) highlights it, a second tap inside the same box (other x, e.g. (165,10)) confirms. Keys do nothing.
* Frame divider in heroine 3D dialogue (first Nene scene, break room): the 3D scene runs a 4-vblank cycle (phase bytes @0x213d2e4+0xa0/a1/a3 cycle (1,0,1)->(2,0,2)->(2,1,2)->(1,0,0)); the touch-screen image changes every 4th frame (15 Hz) while idle, the 2D page every 3rd frame.
* Navigation to this scene: new game from slot 1 -> clock/profile dialogs -> tap (30,100) through the prologue, choices pick option 1 (room-style, "今日からここが…") -> arrives at the Nene meeting in ~100 taps.
