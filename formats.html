Chapter 11

The files

Everything the game shows, plays or decides comes from 301 files on the cartridge. This chapter goes through every format among them, layer by layer: the containers that hold them, Nintendo's standard formats inside those, and the formats Konami made for itself.

The other chapters explain what the game does with its data. This one is the reference for how the bytes are laid out. Each format here has two readers in the project: a Rust loader in lp-engine and a separate Python parser in tools/. The two were written apart and checked against each other on every file the game has. None of the layouts below was copied from anywhere. They were read from the game's own code, or from Nintendo's documentation of its standard formats, and then confirmed on the files.

A map of the cartridge

The cartridge's file system, NitroFS, is an ordinary tree of names. lp-engine's extractor writes it out once (chapter 12), and the tree looks like this:

The program itself is not in the tree. The ARM9's main code and its 44 overlays (chapter 1) sit in their own areas of the cartridge, listed in its header.

The containers

The archive

Almost everything in arc/ and the screen folders is packed into an archive of the game's own design. It's a simple one:

offsetfield
+0magic 0x00015618 (the bytes 18 56 01 00)
+4entry count, 16 bits
+12the entry table: for each entry its offset, stored size and unpacked size (32 bits each), and in some archives a name after them. The table's stride follows from where the first entry's data begins.

An entry whose unpacked size differs from its stored size is compressed. Entries can be archives themselves, and 128 of the 301 files are archives. Unpacked, they hold about 19,000 files.

Compression

Two compressors from Nintendo's SDK appear, and both are kinds of LZ77. A compressed entry starts with a type byte (0x10 or 0x11) and a 24-bit unpacked size. After that comes a flag byte for every eight tokens. A clear flag bit means "copy one byte". A set bit means "repeat earlier output": in type 0x10, 4 bits of length (3 to 18) and 12 bits of distance (1 to 4,096). Type 0x11 adds two longer length codes, for runs up to 65,808 bytes. The save uses the same 0x10 compression. Matching the game's output byte for byte needed its exact search order (chapter 6).

The program code uses a third variant, bottom LZ, which decompresses from the end of the buffer backwards. That lets the code unpack itself in place. The game's own start-up code does it, on the DS and in lp-engine alike, since lp-engine runs that start-up code unchanged (chapter 12). The extractor unpacks the code as well, so the tools can read it.

The cipher

Scripts and text banks are lightly scrambled. The first eight bytes are a four-letter magic number (SBIN or TXRC), a three-byte key and a one-byte multiplier. Every byte from offset 8 on is XORed with a stream made from them:

plain[i] = cipher[i] XOR ((mult × ⌊i / 3⌋ + key[i mod 3]) AND 0xFF)    (i = offset in the file)

Since the key travels with each file, reading these is ordinary parsing: the project embeds no secret. The one real protection on the cartridge, the self-decrypting overlay 1, is never decrypted by our code (chapter 1). The translation's text banks set the key and multiplier to zero, which turns the cipher into a no-op, and the game reads them just the same.

Bundles

Konami's 3D data adds one more container, the bundle: a count, an entry size (always 0x28), then per entry an offset, a size and a 32-byte name. Each heroine motion is a bundle holding two files, one for the joints and one for visibility. The models' companion files (shading tables, palettes, colour variants) come in bundles too.

Nintendo's formats

The game draws, animates and plays sound through NitroSystem, Nintendo's middleware (chapter 1), so its graphics, models and music are in NitroSystem's standard formats. They all share one frame: a header with a four-letter signature stored byte-reversed (an NCGR file starts RGCN), a byte-order mark 0xFEFF, a version, the file size, the header size and a block count. After the header come blocks, each with its own signature and size.

formatwhat it holdsin the game

NCGRtiles (8×8 pixels, 4 or 8 bits each) or bitmaps2,599

NFTRbitmap fonts: glyphs, widths, character maps2

Some things the formats allow, the game never uses. It has no texture-pattern, texture-SRT or material animations. Expressions are texture swaps done in code (chapter 5), which is why that chapter reads more like code than data. Joint animations keep a key every 1, 2 or 4 frames, then one per frame for a tail, and are interpolated linearly. The visibility tracks do double duty: besides hiding meshes, they choose the hand pose and request eye changes.

The sound archive holds 152 sequences, 383 instrument banks and 832 sampled waves (chapter 8). A sequence is NITRO-Composer's byte code: notes, waits, tempo, volume, pan, pitch bend, loops, calls, variables and random branches, at 48 ticks per quarter note. Waves are 8- or 16-bit PCM or IMA-ADPCM, with loop points. The fonts, 10 and 12 pixels tall, are stored turned a quarter turn, matching the way the DS is held (chapter 9).

Konami's formats

Scripts: SBIN

The 1,304 scripts in arc/tmx_event.arc are the game's own format. Once the cipher is removed, the header is big-endian, unusually for the DS. Offset 8 holds the number of entry points, a set of section offsets follows, and the entry offsets start at 0x40. Code and strings live in separate sections. Strings are UTF-8 with a length prefix: one byte, or two when the first has its top bit set. Instructions are [opcode][argument count][arguments as 16-bit words]. The instruction set is in chapter 3's detail section.

Script 899 is no ordinary script. It's the directory: 16,332 sorted pairs of a 32-bit scene id and a reference, where the reference packs slot << 24 | script << 12 | entry. The slot picks one of four tables in the program's data, and those tables turn the script number into a file in the archive.

Text banks: TXRC

The eight text banks hold 22,413 lines between them. The header gives the group count and three tables: groups (subgroup count and first subgroup), subgroups (line count and first line), and lines, one 32-bit word each with the length in the top 10 bits and the offset in the bottom 22. Strings are UTF-8 with no terminator. TextRes_GetCurrentEntry walks it.

Condition lists: TERM_BIN

Chapter 3's candidate lists, 696 files in all (688 in arc/tmx_tbin.arc, the rest in loveplusmode's keyword tables). An 8-byte magic, a record count, 12 header bytes the evaluator never reads, then records:

offsetfield
+0x00scene id
+0x04priority: a passing record only replaces a lower-priority result
+0x08"seen" flag id, which the scene's own script sets when it plays
+0x0ccondition counts of the three groups
+0x18the conditions, three words each: operation, a, b

Backdrops

Which picture hangs behind a scene takes three files to find. arc/tmx_bbin.arc maps a scene id to a background id: a count, then 8-byte records of the id, the background id and two flag bytes. Background ids below 10,001 fall into fixed ranges, one per backdrop archive (bg_room, bg_school, bg_town, bg_sea_side…). Higher ids name archive id / 10,000 directly. A 20-byte record then turns the id, the season and the time of day into a file number (ScheduleText_UpdateState). That number's position in bg_file_no_0N.bin picks the picture: an NCGR, NCLR and NSCR in a row. This chain agrees with every backdrop the real game loaded in our recordings.

Images: GTD

Event pictures, illustrations, kiss-scene faces and many buttons use a small format of Konami's own. It has four flag bytes, then width, height, palette offset and palette length (16 bits each), and the pixel byte count. Pixels are 8-bit indexes into a 15-bit RGB palette, in rows padded to a power of two. One flag value marks an image stored sideways, like the fonts.

The voice bank

Two files in sys/. Siren14Voice.vtb is a table of 40,555 pairs (offset, size), both stored multiplied by 16. Siren14Voice.spp is 221 MB of Siren14 frames, 40 bytes per 20 ms (chapter 8). The decoder's lookup tables aren't in a file at all: they're in the program, and the extractor copies them from the player's own code.

Lip-sync uses a similar pair. lipsync_add.dat holds 40,554 entries (offset, length) into lipsync.dat, a byte per mouth shape: 0 to 4 are the vowels a i u e o and 5 is rest. The game stretches that track over the clip's length.

Events and mail

mail/condition.bin holds 1,028 records of 16 bytes, one per numbered event. Each record starts with a context mask, the bits that must match the moment for the event to qualify (chapter 3). sendinfo.bin holds 490 three-byte records whose two small deltas feed the heroine's event meters. The rest of the condition fields are only partly decoded (chapter 13).

Data that lives in the code

Some of the game's data has no file. The expression tables, the motion table (974 entries), the period and season boundaries, the text rules, the scene-id tables of the event stages, the voice decoder's tables and about 830 strings (names, kana tables, the speech-recognition vocabulary) are all compiled into the program. The extractor writes the program and its overlays out whole, plus a catalogue of where these tables sit. The tools then read each table from the player's own copy by module and address. Nothing of it is in the repository.

How we know

  • The script reader runs all 16,332 entry points with the same trace as its Python twin. The text reader gives the same 22,413 lines.
  • The 2D reader rebuilds all 2,665 resource sets pixel for pixel, the same as the Python exporter, in 3 seconds.
  • The 3D reader matches on 4,503 files: 1,780 meshes, 4,823 textures, 7,454 joint animations and 2,553 visibility animations.
  • The sound archive reader matches. The sequencer produces the same notes on all 151 playable sequences, and the voice decoder is bit-exact against the game's own.
  • The engine's own format tests use synthetic data, so the test suite runs without a single byte of the game.
