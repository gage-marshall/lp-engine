Chapter 12

Inside lp-engine

The first eleven chapters are about the game. This one is about the engine that runs it: how it gets the game off your cartridge, runs code it hasn't ported yet, stands in for the hardware, and proves at every step that it still behaves like the DS.

Your cartridge, once

lp-engine ships with nothing from the game. On first run you point it at your own copy, and the extractor works through it once, writing a content tree:

  • assets/: every file at its cartridge path. Archives are unpacked one level and decompressed, and the script and text cipher is removed (chapter 11). Nothing else is changed. The files stay in the game's own formats.
  • engine/: the program and its 44 overlays, unpacked, plus the data that lives in the code: the expression and motion tables, embedded strings, the voice decoder's tables, the scripts' resource map.
  • manifest.json: which cartridge it came from (its SHA-1) and what each stage found.

From then on the cartridge isn't needed. The engine reads the content tree, with patch/ layered on top (the translation, or any mod) so that a replacement file simply wins. A separate exporter turns the same tree into everyday formats for anyone who wants to look: PNG, glTF, WAV, MIDI, JSON. The engine never reads those.

Power on

The engine starts the way a DS does. It loads the ARM9 program where the cartridge header says, sets up what the firmware would leave behind (the header copy, the boot type, the card ID, the user settings), and jumps to the game's entry point. From there the game's own start-up code runs. It unpacks the compressed program, copies the fast-memory code into place, clears memory, runs the C++ static constructors, and reaches Main_Startup. None of that is reimplemented. It's the game's code doing what it always did.

Running the game's code

Most of the game still runs as its own ARM code, in an interpreter built into the engine. It handles both of the ARM9's instruction sets (ARM and the compact Thumb), the BIOS calls, and the SDK's threads: when the game switches threads, the interpreter switches register sets. Interrupts are delivered through the game's own interrupt table, so its handlers run just as they did, including OS_IrqHandler.

Time has to be invented. The interpreter counts one tick of the SDK's clock for every 85 instructions it runs, and raises the screen refresh every 8,753 ticks (chapter 1). Each run of code stops at the next refresh, so a busy loop can't swallow the interrupt it's waiting for. When the game goes idle, waiting for an alarm or the next refresh, the engine skips ahead to it.

The registry

Every time interpreted code calls a function, the engine checks a registry first. If the function is there, the call goes to native Rust instead:

kindentrieswhat it means
port81a game function rewritten in Rust and checked against the original
SDK edge46an SDK function that touches hardware: the cartridge, PXI, the clock chip, touch, power, DMA, the microphone
subsystem65a function that could be handed to an engine subsystem. Today they all decline, so these run as game code.
pending143named and waiting to be ported. Game code for now.

Above the registry, bigger pieces are native outright: the frame loop (Main_UpdateFrame), the whole game flow from chapter 2, and everything the ARM7 used to do. In one measured stretch of play, from power-on through a whole new game and two later sessions, the interpreter ran 7.1 billion instructions across 3,583 distinct functions. The biggest shares were the voice decoder (17%), NitroSystem's 3D drawing (17%), memory copies and cache upkeep (16%) and the sprite manager (13%).

How a function gets ported

  1. Read it in the decompiler and write it in Rust.
  2. Test it against the original on randomised inputs: the interpreter runs the game's code, the port runs alongside, and memory and the return value must match. The test also records how many instructions the original took, so the port can charge the same time. Otherwise the game's sense of time would drift.
  3. Turn it on, with a shadow check available while the game runs: each call to the port is followed by the original, interpreted on the same state, and the two answers are compared. Over a complete new game that's about 690,000 calls to 26 ports, and every one agrees.

Order matters too. The next function to port is the one costing the most interpreted time, one at a time, each committed before the next.

Standing in for the hardware

The engine reimplements the DS around the game: the memory map, the fast memories, the video memory banks and their routing, the hardware divider and square root, DMA, both 2D engines, the 3D geometry engine and rasteriser, display capture, the cartridge bus, the backup chip, the keys and the touch screen. The ARM7 never runs. Its jobs (sound, touch, the clock chip, the microphone, power) are answered over PXI by native code, written to the protocol the game speaks (chapters 8 and 10). This was a deliberate choice. Emulating the second processor would make lp-engine an emulator, and the project's aim is a game that runs natively, a piece at a time.

The cartridge is a virtual one. The game's file table points into the files of the content tree. A replacement file in patch/ is placed past the end of the original data and the table entry moved to it, so the game's own code loads it, at any size.

Looking like a real console

Some of the game's checks only pass on real hardware, and failing one doesn't crash the game. It quietly changes the game. Its copy protection runs checks from the title screen, and if they fail it installs different versions of a few routines. One of them is how affection grows: gains are divided by five and losses multiplied by five, so the heroines slowly grow cold. Early versions of lp-engine failed two of those checks. The firmware's user settings were missing (a real DS has them in memory, including the console's network address), and the virtual cartridge answered one kind of read differently from a real card. Both were fixed by making the engine behave like the hardware. Nothing in the game is patched. A test now checks that the title screen installs the ordinary routines.

Recording, replay and probing

The game is deterministic given four things: the save it started from, the inputs, the clock and the audio rate. So every session the app plays is recorded as exactly that: the starting save plus a log of inputs and clock readings, keyed by the game's own frame passes. A recording replays pixel for pixel. A bug report becomes a folder that reproduces the bug.

For investigation there's game_probe, the engine without a window. It counts time in screen refreshes, the same way an emulator does, so frame N in the probe lines up with frame N in an emulator run. It takes scripted taps and drags, a fixed starting clock, and a forced scene (--event, through a debug override the game itself reads). It can take screenshots, dump memory ranges over a span of frames, stop at the n-th write to an address, trace sound commands, write the audio to a file, and draw every 3D frame on both the CPU and the GPU to compare them.

Checking against the real game

A claim about the game only counts once it's been compared with the game. The project uses the same few methods throughout:

  • Call logs. The game was played in an emulator with its calls logged. 63 recordings, 311,719 frames and 5.9 million calls are the ground truth that the game flow (chapter 2) is checked against, on every test run.
  • The game's code as oracle. To check a piece of logic, the original machine code runs in an emulator with every call it makes answered by a mock. The port must produce the same answer: 38,304 mocked states for each of the 36 event stages, all 107 condition operations, the save packers (chapters 3 and 6).
  • Python first. Most systems were first modelled in Python (sandbox/, tools/), checked against the game, and only then ported to Rust. The Python models stay as references, and the Rust is checked against them.
  • Whole sessions. One test plays a complete new game from an empty save, about three minutes of work: the clock, the name written by hand and read by the game's own recogniser, the prologue's choices, the tutorial and a save from the room. The emulator played the same script and showed the same screens. The two saves match in every structure except a single field where the game stamps its tick count. The engine's stamp is about 10 frames higher. Its tick counter starts sooner: the engine charges every instruction the same time, and the memory-heavy unpacking at boot, which delays the counter's start, runs slower on a real DS.

What running the game found

A few bugs that only running the real game could reveal:

  • The kiss that never came. The frame loop hands the current capture phase to the task pool, which runs that phase's tasks. The engine's frame loop passed nothing, so phase-1 tasks never ran. One of them is the 2D effect the kiss waits for, and the confession scene hung on a white screen.
  • The clock that started too early. The SDK's tick counter starts when the game starts a hardware timer, not at power-on, and the game's alarms are measured from that moment.
  • Interrupts that shouldn't happen. With interrupts disabled, the DS takes none. The engine was still waking threads, and a screen refresh arrived while the program was still compressed.
  • The clock getters. A mislabelled decompile made the ports read the clock at the wrong offsets. The shadow check caught it on the very first call of the boot: the old port said month 0 and the game said 10.

The touch-release rule and the lid bit in chapter 10 were found the same way.

Mods

Because the engine knows which picture it's drawing, pictures can be replaced without touching the game:

  • Textures are named by a hash of exactly the bytes the texture format reads, plus the palette entries it reaches and its format bits. The same picture gets the same name wherever it sits in video memory. An index built from the content tree turns those hashes into readable names (file/texture@palette), more than 14,000 in all.
  • Backgrounds are rebuilt as whole planes, named by their screen file, so a replacement covers the whole picture rather than single tiles.
  • game --dump-textures DIR writes everything it shows in the same layout, so the dump is a mod's starting point. A PNG of any size dropped into patch/hires/ or mods/ replaces the original. The game still reads the original, and only what you see changes.
  • Files in patch/fs/ replace the game's own files outright, at any size, and the game's own code reads them. The translation uses this.

Naming 15,499 functions

The function map behind every link in this guide was built in stages. First, byte-matching against the SDK and NitroSystem versions the game was built with gave 1,254 exact names. Then every other function got a structural name from its shape and the subsystem whose data it touches, such as Get, Set, Thunk or Proc. Modules and overlays were named from the file names and strings they refer to. Finally the functions that mattered were named by reading them, highest call weight first, and corrected whenever the engine proved a name wrong. The map keeps the old name and marks how sure each name is.
